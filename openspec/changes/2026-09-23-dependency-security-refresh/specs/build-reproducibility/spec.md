# Build Reproducibility Specification

## Purpose

Every install and image build in this repository resolves from a committed lockfile, and the repository carries no stale second container path.

## Requirements

### Requirement: Backend Lockfile Is Committed and Enforced

`backend/Cargo.lock` MUST be tracked; the backend CI step MUST run `cargo test --locked`; and the production image's gated backend build MUST run `cargo build --release --locked`. The lockfile, the CI flag and the Dockerfile flag MUST land in the same commit.

#### Scenario: Clean runner resolves from the lock

- GIVEN a clean CI runner with the Postgres service
- WHEN `cargo test --locked` runs
- THEN resolution succeeds from `backend/Cargo.lock` (the `cargo test --offline` `argon2` failure no longer occurs) and the backend job is green

#### Scenario: Manifest/lock drift fails loudly

- GIVEN a `Cargo.toml` range that disagrees with the committed lock
- WHEN `cargo build --locked` or `cargo test --locked` runs
- THEN the command fails instead of silently re-resolving

#### Scenario: Warm-up build stays tolerant

- GIVEN the dependency-warmup dummy build that runs before sources are copied
- WHEN it fails
- THEN it remains non-fatal by design; only the gated build enforces `--locked`

### Requirement: Lockfile and CI Flag Atomicity

The lockfile commit and the `--locked` CI change MUST NOT be split across commits, because CI changed first stays red.

#### Scenario: Single commit

- GIVEN the change history
- WHEN the backend-lockfile commit is inspected
- THEN it contains `backend/Cargo.lock`, the CI flag and the Dockerfile flag together

#### Scenario: Revert returns to a known state

- GIVEN a revert is needed
- WHEN the commit is reverted
- THEN CI returns to a known-red state with no partial lockfile state left behind

### Requirement: Behind-Latest Transitive Crates Are Named, Not Chased

Apply MUST run `cargo update --dry-run` and record every behind-latest crate in the verify report with the reason it stays. `backend/Cargo.toml` version ranges MUST NOT be widened by this change.

#### Scenario: Named in the report

- GIVEN `cargo update --dry-run` output
- WHEN the verify report is written
- THEN each behind-latest crate is listed with the reason it remains

#### Scenario: No range widening

- GIVEN the backend diff
- WHEN `backend/Cargo.toml` is inspected
- THEN only `tower-http` feature flags may differ and no version range changed

### Requirement: Stale Second Container Path Is Resolved, Never Half-Fixed

`docker/backend.Dockerfile` and `docker-compose.yml` MUST end this change in one coherent state: both deleted, or both refreshed. A compose file pointing at a deleted Dockerfile, or a stale Dockerfile left in place, MUST NOT remain.

#### Scenario: Confirm before deleting

- GIVEN the compose workflow is not used by the owner
- WHEN apply confirms this once
- THEN both files are deleted together and the decision is recorded in the verify report

#### Scenario: Refresh path

- GIVEN the compose workflow is used
- WHEN the pair is refreshed
- THEN `docker/backend.Dockerfile` uses a Rust image satisfying the tree's MSRVs, its build passes `--locked`, and the file states that it serves no static assets unlike the root `Dockerfile`

### Requirement: Install Pinning Is Documented

Documentation MUST NOT instruct an install method that cannot be pinned. `mcp-dashboard/README.md` MUST use `npm ci` and state that the lockfile is committed; wherever install or build steps are documented, the `--locked` / `--frozen-lockfile` / `npm ci` policy MUST be stated; behind-latest transitives MUST be recorded as intentionally not chased.

#### Scenario: README install step

- GIVEN `mcp-dashboard/README.md`
- WHEN the install section is read
- THEN it says `npm ci` and notes the committed lockfile

#### Scenario: Pinning policy is visible

- GIVEN the docs touched by this change
- WHEN a reader looks for build pinning
- THEN the `--locked` / `--frozen-lockfile` / `npm ci` policy is stated

### Requirement: Review Accounting for Generated Lockfiles

Generated lockfiles (`Cargo.lock`, `pnpm-lock.yaml`, `package-lock.json`) MUST be treated as review-exempt; the reviewable unit is the hand-written diff. This change MUST NOT be recorded as a `size:exception`.

#### Scenario: Budget is read on hand-written lines

- GIVEN the change diff
- WHEN review size is assessed
- THEN lockfiles are excluded and the hand-written diff (≈ 250–330 lines) is what is compared against the 400-line budget

## Edge cases

- Without a docker daemon in apply, the image build MUST be recorded as "not evidenced", never inferred from `pnpm build` plus `cargo build` success.
- A lockfile regenerated by another unit (pnpm key deletion, caret floaters) MUST be attributed to that unit, not duplicated here.
- The `Dockerfile` copies `backend/Cargo.lock*` with a tolerant glob; committing the lock makes it real, but only the `--locked` build step enforces it.

## Non-goals

- No `cargo audit` (tool availability unverified) and no new tooling installs.
- No new npm CI job for `mcp-dashboard` in this change.
- No chasing of behind-latest transitive Rust crates and no `Cargo.toml` range edits.
- No Dokploy, Traefik or firewall work.
