# Hermes: renderizador Markdown/Base64, servidor de archivos Rust y uploads multimodal

Feature 1 de la entrega del 2026-10-29. Runner: `vitest` + `tsc` (frontend), `cargo test` en contenedor Rust (backend, ver L3), Playwright (e2e/visual), Judgment Day. DB: producción, cero migraciones. Sin `git commit` ni `git push` (S1).

## Specs

- **S1 — Reglas de entorno (verbatim del dueño).** ODD; backend Rust (Axum) y frontend React/JS de Control Deck; conexión exclusiva a la base de datos de PRODUCCIÓN y **estrictamente prohibido** crear o migrar bases locales; **estrictamente PROHIBIDO** ejecutar `git commit` o `git push`; validación visual con la skill `playwright-cli`; verificación interna ("Judgment Day" / verify) al finalizar.
- **S2 — XSS sanitizado.** "Escapa o sanitiza estrictamente todo el contenido HTML previo al procesamiento de etiquetas `<img>` o enlaces. La respuesta del modelo debe tratarse como no confiable." Aceptación 6: "La inyección de código como `<script>` o `<img onerror=...>` es totalmente escapada y neutralizada".
- **S3 — Markdown completo.** "Sustituye la salida en texto plano por un renderizador de Markdown (ej. `react-markdown` o procesador AST equivalente) que soporte **negritas**, listas, tablas, bloques de código con sintaxis resaltada y enlaces `<a>`."
- **S4 — Base64 inline.** Detectar `data:image/(png|jpe?g|gif|webp);base64,...` dentro del texto acumulado del mensaje y "Reemplaza automáticamente estos patrones por etiquetas `<img src="..." class="max-w-full h-auto rounded-lg my-2 shadow-md" />`". RESTRICCIÓN: "la búsqueda y reemplazo de cadenas base64 debe ejecutarse sobre el **texto acumulado del mensaje completo** (o reacondicionado en cada delta), nunca sobre chunks SSE fragmentados individuales".
- **S5 — Conversión de rutas.** Capturar `/opt/data/...`, `/tmp/...`, `MEDIA:...` y URLs del servidor de archivos. Imagen (`.png`, `.jpg`, `.webp`) → `<img src="/api/hermes/media?path=..." />`. Documento o binario (`.docx`, `.xlsx`, `.pptx`, `.pdf`, `.zip`) → `<FileDownloadCard>` con nombre del archivo, su extensión y un botón **"Descargar archivo"**.
- **S6 — Servidor de archivos.** `GET /api/hermes/media?path=...` con "Normaliza y valida la ruta contra una lista blanca estricta de directorios permitidos (`/opt/data/cache/scratch`, `/opt/data/cache/documents`, `/opt/data/entregables`, `/opt/data/uploads`)", rechazo de `..`, "streaming asíncrono en disco, cabeceras `Content-Type` inferidas (`mime_guess`) y `Content-Disposition: attachment; filename="..."` para forzar la descarga limpia en el navegador sin cargar archivos enteros en memoria RAM".
- **S7 — Imágenes entrantes.** "Conserva el flujo directo codificando las imágenes seleccionadas como partes `image_url` con data URLs dentro del array `content` del mensaje."
- **S8 — Documentos entrantes.** Endpoint `POST /api/hermes/upload` multipart en Rust; guarda en `/opt/data/uploads/` con "nombres sanitizados" e "identifica su URL en la LAN". El frontend sube primero y luego inserta en el texto: `[archivo adjunto: http://<IP_LAN_O_HOST>:<PUERTO>/api/hermes/media?path=/opt/data/uploads/nombre_archivo.docx]`, "de este modo, Hermes puede descargar y leer el contenido del documento mediante sus herramientas locales de terminal (`curl` / lectores de documentos) sin romper el esquema de la API".
- **S9 — Flujo asíncrono intacto.** "Conserva el uso de la API de Runs (`POST /v1/runs` y SSE `GET /v1/runs/{id}/events`), la gestión de tarjetas de aprobación (`waiting_for_approval`), el cronómetro `MM:SS`, la tarjeta de preguntas interactiva estilo Claude UI y la colapsabilidad del pensamiento (`<ThoughtAccordion>`)."
- **S10 — Criterios de aceptación (verbatim).**
  1. Al pedir "genera una imagen de prueba", la imagen se visualiza incrustada directamente en el chat mediante la etiqueta `<img>` (tanto durante el streaming como al finalizar).
  2. Al pedir "genera un Word o PDF", la ruta del servidor se convierte en una tarjeta interactiva con botón de descarga que obtiene el archivo `.docx` o `.pdf` funcional.
  3. Al adjuntar una imagen desde Control Deck, el agente analiza y describe correctamente su contenido visual.
  4. Al adjuntar un documento `.docx` o `.pdf` desde Control Deck, el archivo se sube al servidor en Rust y Hermes accede a él mediante la URL en LAN para procesar su contenido.
  5. Los mensajes con Markdown (**negritas**, listas, bloques de código) se renderizan con estilos tipográficos enriquecidos.
  6. La inyección de código como `<script>` o `<img onerror=...>` es totalmente escapada y neutralizada contra ataques XSS.
  7. El proceso de verificación ("Judgment Day") concluye con éxito confirmando que la paridad con Telegram es completa y estable.

### Desvíos y decisiones (declarados)

- **D-A1 — Raíz extra `documentos_generados`.** S6 no la nombra, pero es el directorio real de entregables medido en el gateway; sin ella el criterio 2 no se cumple. Se suma `/tmp` (S5). La raíz `/opt/data` queda **excluida** a propósito.
- **D-A2 — Resaltado sin dependencias nuevas.** El repo no tiene `rehype-highlight`/`highlight.js`/`shiki` y aquí no hay `pnpm`: se implementa un resaltador determinista (tokenizador por lenguaje sobre nodos de React, sin HTML) para `python`, `bash`/`sh`, `js`/`ts`, `json`, `sql`, `rust` y `diff`. Ningún `dangerouslySetInnerHTML`; cualquier lenguaje no soportado se muestra como bloque plano. Evita sumar superficie de cadena de suministro (contexto: F-08 del audit, repo público).
- **D-A3 — Mount pendiente.** Sin `/opt/data` en el contenedor no hay descarga ni upload reales en producción. Verificado aquí con `HERMES_MEDIA_ROOTS`/`HERMES_UPLOAD_DIR` sobre un fixture temporal; se reporta como acción del dueño, no como defecto de código.
- **D-A4 — URLs firmadas.** `<img>`/`<video>`/`<audio>` no pueden enviar la cabecera de sesión, así que `?path=` a secas no funciona: la URL servible incluye `exp`/`sig` (HMAC-SHA256, ya existente) y la inyección de S8 usa esa forma. El parámetro `path` sigue presente, como pide la spec.
- **D-A5 — `<FileDownloadCard>` ya existe como `ArtifactCard`.** El componente cumple la spec (nombre, extensión con badge, botón `hermes.downloadDocument = "Descargar archivo"`, `Content-Disposition: attachment`); no se renombra para no romper 40+ tests ni el contrato interno.
- **D-A6 — Imágenes remotas siguen bloqueadas.** S4 habilita `data:image/*` y URLs firmadas del propio proxy dentro del Markdown; un `![x](https://tercero/...)` sigue sin renderizarse, para que la salida del agente no pueda hacer beaconing. Es la decisión de seguridad ya documentada y no la contradice la spec.

## Operación y límites conocidos

### Variables de entorno del backend

- **`HERMES_PUBLIC_BASE_URL`** — base absoluta con la que se arma la URL que el agente va a buscar (p. ej. `https://panel.example.com`, sin `/api`). Manda sobre cualquier cabecera. Sin ella se usa el `Host` de la petición, así que detrás de Traefik el agente recibe un `http://…` interno y el `curl` falla aunque la firma sea válida.
- **`HERMES_TRUST_FORWARDED=1`** — habilita `X-Forwarded-Host`/`X-Forwarded-Proto` para armar esa URL. Sin la variable se **ignoran a propósito**: un llamante autenticado podría fijar `http://attacker/…` como URL que el agente descarga. Con Traefik delante (TLS terminado ahí) hay que activarla para que la referencia `[archivo adjunto: …]` sea `https` y apunte al host público; con acceso directo por LAN se deja apagada.
- `HERMES_UPLOAD_DIR` (default `/opt/data/uploads`), `HERMES_MEDIA_ROOTS` (allowlist separada por `:`), `HERMES_MEDIA_SECRET`, `HERMES_MEDIA_TTL_SECS` — descritas en el código. El barrido de `*.part` al arrancar usa `HERMES_UPLOAD_DIR`.

### Lo que ya no produce tarjeta (por diseño)

Un archivo que el agente deje **directamente** bajo `/opt/data` (p. ej. `/opt/data/entrega.pdf`) ya no se convierte en tarjeta: la raíz `/opt/data` está excluida de la allowlist porque ahí viven `.env`, `auth.json` y `config.yaml`. Las rutas servibles son las seis raíces de S6 + `documentos_generados` + `/tmp`.

### Límites que esta entrega NO arregla (deliberados)

- **Sin retención ni GC de uploads.** `POST /api/hermes/upload` copia el archivo y nada lo borra: el dueño limpia `HERMES_UPLOAD_DIR` a mano. Lo único automático es el barrido de `.part` incompletos en el siguiente arranque (una pasada, no por request).
- **Una copia duplicada por reintento.** Reintentar un turno fallido vuelve a subir el documento, así que el mismo PDF queda dos veces en disco con dos URLs firmadas.
- **El Markdown se parte en varios árboles de render alrededor de cada imagen.** Cada segmento se renderiza como Markdown independiente: una lista o un bloque que cruce una imagen inline pierde la continuidad.
- **Un payload dentro de backticks inline no se salta.** Solo los bloques cercados (tres backticks o `~~~`) se excluyen; un `data:image/...` entre backticks simples se evalúa como candidato.
- **El escaneo sigue siendo cuadrático en el peor caso.** El tope de `MAX_INLINE_IMAGE_CHARS` corta el crecimiento de un payload incompleto (emite `oversized` en vez de `pending`), pero el texto acumulado se recorre entero en cada flush (~19 ms por flush con el tope de 8 MB). Un parser incremental queda para otra ronda.
